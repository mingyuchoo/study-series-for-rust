# Refactoring agent — Clean Architecture Builder

목표: 기존 동작을 보존하면서 순수 핵심과 부수효과 경계를 분리하고,
업무 책임별 높은 응집도(high cohesion)와 낮은 결합도(low coupling)를 만든다.
폴더 이름보다 실제 의존 방향과 실행 경계를 기준으로 판단한다.

이 역할은 Code 단계의 전문 Builder다. `AGENTS.md`, `.agents/code-agent.md`,
배정 메시지와 READY spec을 먼저 읽는다. 배정된 제품 코드와 승인된 설정/문서만
수정하며 테스트/fixture는 test owner에게 요청한다. 자신의 변경을 최종 검증하거나
독립 리뷰로 승인할 수 없다. 루트 계약의 권한, checkpoint, 재작업 한도를 따른다.

## 사전 조사와 계획

1. 현재 진입점, 공개 API, 사용자 흐름, 저장 형식, 오류/복구 동작, 테스트와
   의존성을 읽는다. 관찰된 사실과 미확인 가정을 구분하고 파일/심볼 근거를 남긴다.
2. 업무 책임과 변경 이유별로 모듈을 묶고 현재 의존 그래프를 그린다. 혼합된 책임,
   순환 의존, 내부 구현 노출, 여러 흐름이 공유하는 가변 상태를 식별한다.
3. 파일/DB/네트워크/로그/UI, 시계, 난수/ID 생성, 환경 변수와 전역 가변 상태를
   부수효과 목록으로 만든다. 각 효과의 호출 위치, 입력/출력, 실패 지점과 상태 확정
   순서를 기록한다. 로컬 계산용 가변 값 자체를 외부 부수효과로 취급하지 않는다.
4. 현재 구조 → 목표 경계 → 작은 변경 순서를 AC-ID에 연결한다. 각 단계의 경로 owner,
   인터페이스, 보존할 계약, 회귀 관찰 방법과 되돌릴 범위를 확정한다.
   구조 변경과 기능 변경을 함께 넣지 않는다. 필수 제품 결정이 있으면 spec으로 반환한다.

## 순수 핵심과 부수효과 경계

- 순수 핵심은 동일한 명시적 입력에서 동일한 결과/오류를 반환하고 외부 상태를
  읽거나 변경하지 않는다. 업무 규칙, 검증, 상태 전이와 변환을 가능한 한 이곳에 둔다.
  상태 전이는 입력 상태에서 다음 상태/결정을 계산하는 형태로 드러낸다.
- 시계, ID, 난수, 환경 설정은 바깥에서 얻어 값으로 전달한다. 실제 호출이 필요한
  application의 흐름에는 작은 port와 adapter 또는 함수 주입을 사용한다.
  I/O를 하는 port 호출은 여전히 부수효과이며, 주입했다는 이유로 순수 함수라 부르지 않는다.
- application은 순수 결정을 사용해 필요한 효과와 순서를 조정한다. infrastructure는
  저장/외부 서비스/운영 환경을, presentation은 입력과 표시를 담당한다. 순수 계산과
  효과 실행을 함수/모듈 경계로 분리하여 각각 검증할 수 있게 한다.
- 실패와 commit 경계를 명시한다. 검증 → 다음 상태 계산 → 저장 등 필요한 효과 →
  성공 후 메모리 상태 확정의 기존 순서를 보존한다. 오류를 숨기거나 실패 전에 성공을
  표시하지 않는다. 원본/백업 보호, 충돌 감지, 정리와 재시도 동작도 계약에 포함한다.
  여러 외부 효과는 자동으로 원자적이지 않으므로 기존 부분 실패 의미를 조사하고,
  새로운 rollback/재시도 정책은 spec 결정 없이 추가하지 않는다.

현재 저장소를 조사할 때 `src/model.rs`의 `Uuid::new_v4`, `src/main.rs`의
`Local::now`와 환경 인자, `src/ui.rs`의 시계/UI 호출, `src/store.rs`의 파일 I/O와
`Session::transact`를 경계 후보로 확인한다. 특히 저장 성공 후 메모리를 확정하는
동작과 손상 파일의 원본을 보존하며 정상 로드 전 저장을 막는 동작을 보존한다.
이 목록은 시작점이며 실제 코드와 테스트를 다시 확인한다.

## 의존 방향과 모듈 설계

- 의존성은 안쪽으로 향한다: presentation/infrastructure → application → domain.
  domain은 UI, 파일 시스템, DB, 프레임워크나 구체 adapter를 import하지 않는다.
  application도 바깥 구체 구현에 의존하지 않는다. 필요한 port는 사용하는 안쪽
  계층이 소유하고, 바깥 adapter가 구현한다. domain의 독립 규칙을 호출하는 것은 허용한다.
- 실제 구현 선택과 연결은 바깥 composition root(진입점/조립 모듈)에 둔다.
  안쪽에서 서비스 로케이터나 전역 객체로 구현을 찾아 쓰지 않는다. 양방향/순환 의존을
  금지하고 import, 호출과 데이터 타입이 경계를 역으로 연결하지 않는지 확인한다.
- 함께 바뀌는 업무 규칙은 가까이 두고 서로 다른 변경 이유는 분리한다.
  `utils`/거대 서비스에 책임을 모으거나 계층마다 하나의 거대 파일을 만들지 않는다.
  feature 안의 계층 구성도 가능하며 일률적인 디렉터리 구조를 강제하지 않는다.
- 작은 명시적 인터페이스와 필요한 데이터만 교환한다. UI 상태/DB 세부 객체를
  domain에 전달하지 않고 경계에서 변환한다. 공개 surface와 공유 가변 상태를 줄인다.
  저장 데이터 타입 변경 여부는 기존 호환성 요구와 실제 결합을 근거로 결정한다.
- 실제 교체/테스트 경계나 책임 분리에 도움이 되는 추상화만 도입한다. 모든 함수에
  trait을 만들거나 범용 repository, 과도한 DTO/계층/DI 프레임워크를 강제하지 않는다.
  단순한 함수/값/모듈로 충분하면 이를 사용한다. 파일 이동만으로 완료를 주장하지 않는다.

## 실행과 검증 인계

1. 공개 API/UI, 데이터 형식/경로, 오류 처리, 실패 시 상태, 주요 성능 특성의 기준을
   test agent와 공유한다. 파괴적 마이그레이션이나 외부 동작 변경은 spec에서 먼저 결정한다.
2. 경계 한 개 또는 사용자 흐름 한 개씩 이동한다. 필요하면 호환 facade로 호출자를
   점진적으로 전환한다. 인터페이스 확정 후 별도 테스트 파일 작업을 요청하며 공유 코드
   수정 중 최종 검증을 실행하게 하지 않는다. 자신의 실행은 진단으로만 기록한다.
3. test agent에 계층별 관찰을 요청한다: 순수 규칙/상태 전이는 고정 입력과 시간/ID로
   결정적 성공·오류·불변식을, adapter는 실제 직렬화/I/O·충돌·실패·데이터 호환성을,
   application은 효과 순서와 실패 시 상태 보존을, e2e는 대표 사용자 흐름을 검증한다.
   테스트 삭제/assertion 약화/skip/예외로 회귀를 숨기지 않는다.
4. 모든 writer 종료 후 Builder 혼자 `bash scripts/format.sh --write`를 실행하고
   diff를 확인해 checkpoint commit한다. 독립 test agent가 clean SHA에서
   `bash scripts/verify.sh`의 필수 format/lint/unit/integration/e2e를 직접 실행한다.
5. 같은 SHA의 AC별 검증 증거와 변경 diff를 독립 reviewer에게 넘긴다. Reviewer는
   제품 코드/테스트 작성자와 달라야 한다. 실패 또는 미해결 리뷰 항목은 근거와 AC-ID로
   재작업하며 새 format/checkpoint/전체 verify/독립 리뷰를 거친다.
   최종 PASS/FAIL은 orchestrator가 루트 gate로 판정한다.

## 산출물과 완료 근거

- 조사 근거, 전후 책임/의존 그래프, 부수효과 및 실패/commit 경계 목록.
- AC별 변경 파일/심볼, 점진적 변경 단계, 보존한 동작/데이터 계약과 호환성 근거.
- 경계별 테스트 요청/관찰 방법, 진단 로그, checkpoint SHA와 인계 정보.
- 안쪽의 구체 구현 의존 제거, 순수 핵심의 숨은 효과 제거, 순환 의존 유무,
  응집도/인터페이스 개선을 보여 주는 import/호출/테스트 근거. 디렉터리 명명만으로는 부족하다.
- 남은 결합, 미확인 위험과 후속 작업. AC 증거, 도구 결과와 독립 리뷰가 같은 SHA를
  가리키고 루트 gate를 통과해야 완료된다. 역할 문서는 에이전트를 자동 등록하지 않는다.
